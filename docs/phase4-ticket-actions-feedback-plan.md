# Phase 4 Plan: Ticket Actions, Feedback, and Audit Writes

## Goal

Make NexusOne Copilot action-capable while keeping the same permission model used by RAG and SQL.

Phase 4 adds:

- Ticket creation previews through chat for IT, HR, and Admin requests, followed by explicit server-checked approval.
- Server-held clarification/preview state for missing required ticket fields.
- Safe ticket persistence in PostgreSQL.
- Feedback capture from the frontend.
- Audit metadata writes for chat turns and tool actions.

This phase should not weaken the current default-deny model. All action paths must resolve the user server-side, validate permissions before writing, and return only safe display fields.

## Current Foundation

Already available:

- `tickets` and `ticket_events` tables in `data/postgres/init/001_schema.sql`.
- `feedback` and `audit_logs` tables in `data/postgres/init/001_schema.sql`.
- Safe ticket read helpers in `data/postgres/init/005_permission_safe_views.sql`.
- SQL subgraph support for own-ticket and queue-safe status lookup.
- Main orchestrator with deterministic guardrail precheck, routing, RAG, SQL, validation, final composition, and trace output.
- Frontend shell with profile switching, chat, citations, SQL sources, and trace display.

## Design Principles

- Ticket writes are deterministic backend tools, not free-form SQL generated by the model.
- The LLM may help classify or draft user-facing wording, but it must not decide authorization.
- Every ticket action requires a server-side user profile.
- Missing required fields should produce `needs_clarification`, not a partial ticket.
- Created ticket responses should show safe fields only: ticket id, department, category, priority, status, and next step.
- `requester_id` is an immutable server-owned creator field. It is written from the authenticated profile in every create path, and is never accepted from chat, model, query, or client input.
- Raw `requester_id`, `assigned_to`, `actor_user_id`, SQL text, and hidden parameters stay out of final answers and frontend payloads.
- Ticket creation always starts with `visibility_scope = 'own'`; widening visibility and assignment are separate authorized support workflows, not ordinary-user request fields.
- Read helpers apply the same `can_user_access_ticket` predicate to list, detail, event, comment, and status lookups. Ordinary users receive creator-owned rows; queue roles receive only server-routed assigned rows in their role/department/group scope.
- Close transitions use a separate server-side eligible-status and HR/IT/Admin group predicate; status changes are persisted as ticket events.
- Feedback and audit writes store safe metadata only.

## Ticket Creation Scope

Supported departments in this phase:

| Department | Example categories | Who can create |
|---|---|---|
| IT | software_access, cloud_access, laptop_issue, vpn, mfa | active users |
| HR | payroll_question, benefits, leave_support, onboarding | active users |
| Admin | access_card, seating, visitor, facilities | active users |

Finance ticket creation is intentionally deferred unless requirements explicitly add it. Finance has more sensitive data handling and should be implemented after the write path is proven on IT, HR, and Admin.

## Required Ticket Fields

The backend ticket tool should require:

- `department`
- `category`
- `priority`
- `description` / non-empty comment-details field
- explicit approval after the preview
- `requester_id` from the authenticated server-side profile, never from user input; the database trigger rejects later requester changes

Optional fields:

- `title` if we add it to the API response model only; the current DB table does not have a title column.
- `visibility_scope`, fixed to `own` for this create path; queue/manager scopes require a separate authorized workflow.
- `metadata` is deferred because the current schema does not include a JSON metadata column.

## Database Access

Use parameterized SQL only.

Ticket creation should:

1. Generate a deterministic department-prefixed ticket id, for example `IT-5001`.
2. Insert into `tickets`.
3. Insert a `ticket_events` row with `event_type='created'`.
4. Return a sanitized DTO.

Feedback submission should:

1. Validate `rating` against the table constraint.
2. Trim and length-limit `comment`.
3. Insert into `feedback`.
4. Return feedback id and status.

Audit writes should:

1. Store safe metadata after each chat turn.
2. Store `conversation_id`, `turn_id`, `user_id`, `role`, intent/route, tool names, status, latency.
3. Avoid source chunk text, full final answers, SQL text, prompts, and hidden fields.

## Orchestrator Changes

Add a deterministic action route before normal RAG/SQL branching:

```text
load_user_context
  -> precheck_guardrails
  -> route_question
  -> collect_ticket_fields?       when user asks to create/open/raise a ticket
  -> validate_ticket_request
  -> create_ticket OR ask_clarification
  -> compose_final_answer
  -> finalize_response
```

New response statuses:

- `needs_clarification`
- `needs_approval`
- `ticket_created` (only after explicit approval)
- `not_created` (approval denied)
- `ticket_closed`
- `comment_added`
- `error`
- existing `answered`, `validated`, `denied`, `no_answer`

Clarification and approval state is server-controlled:

- The graph extracts fields, while `TicketService` stores the draft/preview against authenticated user plus conversation.
- If required fields are missing, it returns a structured `missing_fields` list and explicitly asks for team, category, priority, and non-empty details.
- A preview is persisted nowhere in `tickets`; only a clear approval message can consume it, and duplicate approval is idempotently rejected.

## Routing Rules

Ticket creation route should trigger on phrases such as:

- `create a ticket`
- `raise a ticket`
- `open an IT ticket`
- `I need help with my laptop`
- `request access card`
- `payroll issue`

Ticket status lookup remains SQL route:

- `show my ticket status`
- `who is handling IT-1046`
- `what is the status of my ticket`

This separation matters because creation is a write action, while status lookup is a read-only SQL subgraph path.

## Frontend Changes

Add:

- Feedback controls on assistant answers: helpful, not helpful, report source issue.
- Ticket-preview rendering with requester display name, route, details, and explicit Approve/Cancel actions.
- Ticket-created rendering with ticket id, status, department, and next step.
- Clarification rendering for missing fields.
- Disabled/loading/error states for feedback and ticket actions.
- Non-leaky error state if feedback or ticket creation fails.

The frontend should not decide whether a user can create tickets. It only sends the current selected profile and message; backend authorizes and validates.

## API Changes

Add endpoints to the stdlib dev server:

- `POST /api/chat` remains the primary chat and preview/approval entry point.
- `GET /api/tickets` and `GET /api/tickets/{ticket_id}` use the authenticated ticket predicate.
- `POST /api/tickets/{ticket_id}/comments` requires non-empty comment text.
- `POST /api/tickets/{ticket_id}/close` requires non-empty resolution details and server-authorized HR/IT/Admin access.
- `POST /api/feedback` stores answer feedback.

Candidate feedback payload:

```json
{
  "conversation_id": "web-chat",
  "turn_id": "web-turn",
  "user_id": "u001",
  "rating": "helpful",
  "comment": "The citation helped."
}
```

Ticket creation should be handled through `/api/chat` first so users can ask naturally.

## Tests

Backend unit tests:

- Complete employee ticket details return a preview and do not write before approval.
- Employee can approve IT/HR/Admin tickets; server routing exposes them only to the matching queue group.
- User A versus User B list/detail isolation is enforced.
- Missing category or non-empty comment/details returns `needs_clarification`.
- User-supplied requester id is ignored.
- Inactive or unknown user cannot create a ticket.
- Ticket event is written after ticket creation.
- Feedback rating validation rejects unknown values.
- Feedback comments are length-limited.
- Audit write excludes final answer text, source chunks, SQL text, and hidden ids.

Graph tests:

- Ticket creation route does not call RAG or SQL.
- Ticket status still routes to SQL.
- Prompt injection mixed with ticket creation is denied before write.
- Ticket-created response contains safe fields only.

Frontend/static tests:

- Feedback buttons exist and call `/api/feedback`.
- Ticket-created responses render as a normal assistant result.
- Clarification responses show missing field prompts.

Integration smoke tests when Postgres is running:

- Create ticket through `/api/chat`.
- Confirm row exists in `tickets`.
- Confirm row exists in `ticket_events`.
- Submit feedback through `/api/feedback`.
- Confirm row exists in `feedback`.

## Success Criteria

Phase 4 is complete when:

- Users can create IT, HR, and Admin tickets from chat.
- Missing fields produce a clear clarification response.
- Only approval writes both `tickets` and `ticket_events`; denial and duplicate approval do not write.
- Ticket status lookup still uses the SQL subgraph and remains read-only.
- Comments and authorized close transitions use the same requester/assignment predicate and persist status/events.
- Feedback is stored through `/api/feedback`.
- Audit metadata is written without sensitive content.
- Restricted or malicious requests cannot trigger ticket writes.
- Unit tests and compile checks pass.
- Live Postgres smoke tests pass when the DB is running.
- `docs/agent-loop-status.md` records requirement coverage for R7, R10, and R11.

## Implementation Order

1. Add ticket, feedback, and audit service modules with unit tests.
2. Add ticket action routing and graph nodes.
3. Wire ticket action route into the main orchestrator.
4. Add `/api/feedback`.
5. Update frontend ticket-created, clarification, and feedback states.
6. Add graph and service regression tests.
7. Run full tests and live Postgres smoke checks.
8. Update status docs.

## Risks and Tradeoffs

- Stateless clarification is simpler and safer for the first implementation, but less convenient than true multi-turn form filling.
- The current `tickets` schema does not include `title` or arbitrary metadata; adding those would require a migration and is deferred.
- Ticket id generation must avoid collisions in real concurrent use. For this demo phase, a transaction with department prefix and sequence-style lookup is acceptable; production should use a database sequence or UUID-backed public id.
- Feedback is useful for evaluation but can contain sensitive user text. Comments should be length-limited and treated as internal data.
